# План реализации протокола печати v2

## Цель и границы

Добавить long polling и подтверждение доставки заданий поверх существующего компонента печати, сохранив работу v1.

- Рабочие места — строго положительные целые числа: `1`, `2`, `3` и далее.
- Строковые идентификаторы мест из `long-polling.md` не поддерживаем. Колонка `seat_id` остаётся целочисленной.
- Клиент печати и CRM в объём работ не входят.
- Для первой реализации используем существующие Laravel и СУБД. Отдельный сервис и Redis не требуются.
- Серверные параметры и способ блокировки уточняем после обследования production.

## 1. Зафиксировать совместимость протоколов

Сохраняем существующий адрес получения задания. Версия выбирается исключительно заголовком, а не параметром `wait`.

| Запрос | Поведение |
|---|---|
| Без `X-Print-Protocol: 2` | v1: немедленный ответ, прежний JSON, задание считается полученным при выдаче |
| С `X-Print-Protocol: 2`, без `wait` или `wait=0` | v2: немедленный ответ, задание ожидает ACK |
| С `X-Print-Protocol: 2`, `wait=1…25` | v2: ожидание задания до указанного срока |
| С `X-Print-Protocol: 2`, `wait>25` | v2: ожидание ограничивается 25 секундами |

Для v1:

- Не добавлять ожидание, даже если передан `wait`.
- Не требовать ACK.
- Сохранить HTTP-коды, поля ответа и `{"message":"No job found"}`.
- Не добавлять ответный заголовок `X-Print-Protocol: 2`.

Для v2 возвращать `X-Print-Protocol: 2` с заданием и с пустым ответом. Ошибки компонента возвращать в JSON; заголовок версии сохранять на обрабатываемых приложением ошибках v2.

До реализации описать контракт и явно закрепить отличия от `long-polling.md`: целочисленные места и поведение ACK для ещё не выданного задания.

## 2. Подготовить таблицу заданий

В `print_jobs` добавить:

| Поле | Назначение |
|---|---|
| `status` | `queued`, `sent`, `delivered`; по умолчанию `queued` |
| `sent_at` | Время последней выдачи |
| `delivered_at` | Время подтверждения |
| `send_count` | Число выдач, по умолчанию 0 |

Добавить индекс `(seat_id, status, id)`. Необходимость дополнительного индекса для просроченных `sent` проверить по плану запроса и объёму таблицы.

Миграция должна быть добавочной:

- Существующие задания остаются в очереди и получают `queued`.
- `id`, `seat_id`, `file` сохраняются.
- Старый код продолжает работать после миграции.
- Все существующие обработчики создания заданий получают `queued` через значение по умолчанию.

Не использовать `continue_print_job` как замену статусам: поле не выражает состояния нового протокола.

## 3. Вынести получение задания в общий сервис

Оба протокола должны получать задания через один механизм атомарного выбора. Иначе старый обработчик сможет забрать запись параллельно с новым.

Алгоритм:

1. Начать короткую транзакцию.
2. Найти задание нужного места: `queued` либо `sent`, у которого истекли 60 секунд.
3. Выбирать по `id`, начиная с самого старого.
4. Заблокировать выбранную запись.
5. Для v2 поставить `sent`, обновить `sent_at`, увеличить `send_count`.
6. Для v1 сохранить существующую семантику удаления после успешного чтения PDF.
7. Завершить транзакцию.

Для подтверждённой production MariaDB 10.11.9 / InnoDB использовать `FOR UPDATE SKIP LOCKED` внутри короткой транзакции. В Laravel передать явное выражение блокировки через `lock('FOR UPDATE SKIP LOCKED')`. Конкурентность проверить на MariaDB той же ветки, включая гонки с ACK и созданием заданий.

Время ожидания long polling никогда не должно проходить внутри транзакции. Чтение и подготовку PDF организовать так, чтобы ошибка не приводила к потере задания, а блокировки удерживались минимальное время.

Для v1 в первой реализации сохранить физическое удаление записи, чтобы уменьшить изменения существующего поведения. Для v2 сохранять доставленные записи, чтобы повторный ACK возвращал 200.

## 4. Добавить ожидание v2

В обработчике получения задания:

- Проверять заголовок протокола.
- Проверять `wait`: целое неотрицательное число; максимум фактического ожидания — 25 секунд.
- Сначала сразу пытаться получить задание.
- При пустой очереди повторять проверку примерно раз в 500 мс до истечения срока.
- При появлении задания сразу возвращать ответ.
- Срок ожидания измерять монотонными часами.
- Между проверками не удерживать блокировки и транзакции.

Маршруты получения и ACK выделить в группу без сессий, сохранив адреса. Не переносить их автоматически под существующий общий API-лимит 60 запросов в минуту: несколько мест и подтверждения могут его исчерпать.

## 5. Добавить ACK

Новый маршрут:

```http
POST /print/get-labels/{seat_id}/ack
X-Print-Protocol: 2
Content-Type: application/json

{"task_id":"42544"}
```

Поведение:

- `sent` своего места → `delivered`, HTTP 200.
- Уже `delivered` своего места → HTTP 200 без изменения первого времени подтверждения.
- Неизвестное задание или другое место → HTTP 404.
- Некорректное тело → HTTP 422.
- `queued`, которое ещё не выдавали, не подтверждать; предлагаемое поведение — HTTP 409.

Последний случай в исходном документе не определён; закрепить его в серверном контракте.

ACK и повторная выдача должны корректно работать при одновременном обращении к одной записи.

`delivered` означает, что клиент сохранил PDF, а не что принтер завершил печать.

## 6. Учесть остальные обработчики печати

Проверить все три способа создания заданий:

- Готовый файл: `/print/add-jobs`.
- Наклейка маркетплейса: `/print/add-label`.
- Генерируемая наклейка: `/api/print/generate-label`.

В этой части:

- Сохранить существующие форматы запросов.
- Использовать положительные целочисленные места; не вводить строковую адресацию.
- Не запрещать попутно числовые представления, которые текущие входы уже принимают, без проверки совместимости.
- В Ozon и Яндекс заменить имена файлов на основе `time()` уникальными именами: повторная доставка должна читать тот же PDF без риска перезаписи.
- Проверять отсутствие файла, сигнатуру PDF и размер перед выдачей.
- Ошибка чтения не должна уничтожать задание или помечать его доставленным.

Отдельно разобрать старые маршруты:

- `/print/get-task/{taskId}`.
- `/print/confirm-task/{taskId}`.

Их существующие сценарии должны сохраниться. При этом они не должны удалять историю подтверждения v2 или возвращать доставленные задания как ожидающие. Для этого предусмотреть явную обработку новых состояний и проверить фактических потребителей старых маршрутов.

Автоматическое удаление проблемных заданий не добавлять: ошибка файла должна быть видна в журнале. Политику очистки `delivered` и PDF определить отдельно с учётом повторного ACK. Не очищать таблицу способом, который сбрасывает идентификаторы заданий.

## 7. Проверить поведение до выката

| Область | Что проверяем |
|---|---|
| v1 | Немедленная выдача, прежний JSON, удаление задания, отсутствие повторной выдачи и заголовка v2 |
| Выбор версии | Один `wait=25` без заголовка не включает v2 |
| v2 | Выдача переводит в `sent`, ACK переводит в `delivered` |
| Ожидание | Пустой запрос завершается примерно через 25 секунд; новое задание возвращается при следующей проверке |
| Повтор | До истечения 60 секунд задание не выдаётся повторно, после — выдаётся с прежним ID и PDF |
| ACK | Повторный — 200; чужое место и неизвестный ID — 404; некорректное тело — 422 |
| Не выданное задание | ACK для `queued` обрабатывается согласно закреплённому контракту |
| Изоляция | Задания места 2 не выдаются месту 1 |
| Конкурентность | Два запроса не получают одно задание в пределах срока ожидания ACK |
| Гонка ACK и повтора | Подтверждённое задание не возвращается в очередь из-за конкурентного обновления |
| Ошибки | Отсутствующий или повреждённый PDF не теряется молча |
| Старые маршруты | Получение и подтверждение по ID сохраняют согласованное поведение |
| Создание | Все существующие способы создания формируют доступные задания |
| Откат | Отключение v2 не приводит к повторной выдаче `delivered` |

Проверки блокировок проводить на той же СУБД, что используется на сервере. SQLite недостаточно для доказательства конкурентной выдачи.

## 8. Обследовать сервер

Пользователь подключается к серверу и предоставляет данные. Пароли, ключи и полный `.env` для обследования не нужны.

| Что выяснить | Какие данные нужны |
|---|---|
| Как обслуживается сайт | nginx/Apache, PHP-FPM/другой режим, наличие контейнеров |
| PHP | Версия PHP именно веб-процесса, используемый FPM-пул |
| PHP-FPM | `pm`, `pm.max_children`, `request_terminate_timeout`, `memory_limit`, `max_execution_time` |
| Веб-сервер | Конфигурация сайта с `fastcgi_read_timeout` или `proxy_read_timeout` |
| Внешние прокси | Наличие CDN, балансировщика, WAF и их таймауты |
| База данных | MySQL/MariaDB/PostgreSQL и точная версия |
| Таблица | Структура и индексы `print_jobs`, движок таблицы, число записей |
| Нагрузка | CPU/RAM, занятость FPM, очередь ожидания и достижение `max_children`, если метрики доступны |
| Файлы | Доступ веб-процесса к PDF, объём каталога, существующая очистка |
| Развёртывание | Как запускаются миграции, обновляется код и сбрасывается OPcache |
| Потребители | Число одновременно опрашиваемых мест и использование старых `get-task` / `confirm-task` |

Для PHP-FPM закладывать по занятому воркеру на каждый открытый long-poll запрос плюс запас для ACK, создания заданий и остальных запросов. При недостаточном запасе рассмотреть отдельный FPM-пул для печати.

Проверить таймауты всей цепочки хотя бы на 40 секунд. Одного `set_time_limit()` недостаточно: он не управляет таймаутами веб-сервера и внешних прокси.

Long polling сокращает количество HTTP-запросов, но проверка каждые 500 мс увеличивает частоту обращений к очереди БД. Учесть это при оценке нагрузки.

## 9. Порядок выката

1. Снять резервную копию и проверить миграцию на копии базы.
2. Применить добавочную миграцию, пока работает старый код.
3. Выложить сервер с поддержкой обеих версий.
4. Проверить v1 и v2 на свободных местах, например 98 и 99, используя искусственные PDF.
5. Проверить реальное 25-секундное ожидание через внешний адрес, включая все прокси.
6. Проверить параллельно ожидающие запросы, ACK и создание заданий.
7. Наблюдать за ошибками, повторными выдачами и занятостью воркеров.

Одновременную работу старого и нового клиентов на одном месте не использовать как штатный режим: задания будут распределяться между ними. Совместимость обеспечивается на уровне API; при переключении конкретного места старый клиент закрывают. Изменение клиента в серверные работы не входит.

## 10. Безопасный откат

Предусмотреть серверный переключатель v2 и безопасный режим возврата к немедленной выдаче.

Откат должен отключать v2, сохраняя код, который понимает новые статусы. При отключённом v2 сервер не объявляет поддержку протокола 2 и работает по правилам v1, исключая доставленные задания из выдачи.

Нельзя возвращать исходный контроллер поверх таблицы с сохранёнными `delivered`: он выбирает любую запись места и может повторно выдать уже доставленное задание.

Не удалять новые поля и историю доставки во время оперативного отката. Отдельно проверить судьбу `sent`: после истечения срока неподтверждённые задания должны оставаться доступными для безопасной повторной выдачи.

## 11. Оценка и критерии готовности

Предварительная оценка серверной реализации — 2–3 рабочих дня, включая миграцию, совместимость v1, ACK, повторную доставку и проверки конкурентности. Проверка и настройка production могут потребовать дополнительного времени.

Работа готова, когда:

- Пройдены проверки v1 и v2 из раздела 7.
- Подтверждены версия СУБД, корректность блокировок, таймауты и запас воркеров.
- Проверено ожидание через внешний адрес сервера.
- Проверен безопасный откат без повторной выдачи доставленных заданий.
- Зафиксированы настройки, контракт и порядок эксплуатации компонента печати.

По предоставленным конфигурациям подтверждён nginx перед Apache:

- HTTP: nginx проксирует запросы приложения на `http://217.25.89.196:8080`.
- HTTPS: nginx проксирует запросы приложения на `https://217.25.89.196:8443`.
- Продолжение цепочки до PHP-FPM подтверждено позже конфигурациями Apache, см. следующий подраздел.
- Корень статических файлов: `/home/admin-domain/web/mp.kidsberry.org/public_html/public`.
- В глобальной конфигурации `proxy_read_timeout=300s`; в предоставленных блоках домена переопределений нет. На участке nginx → Apache увеличение таймаута для 25-секундного ожидания не требуется.
- Глобальный `fastcgi_read_timeout=300s` также присутствует, но в показанных маршрутах домена используется `proxy_pass`, а не прямое подключение nginx к PHP-FPM.
- Определены зоны и параметры `proxy_cache` / `fastcgi_cache`, но в показанных конфигурациях домена и результатах поиска нет директив включения кеша `proxy_cache <zone>` / `fastcgi_cache <zone>`. Оснований считать кеширование ответов печати активным по этим данным нет.

- `nginx -T` сообщает об успешной проверке синтаксиса.
- В конфигурацию включён `cloudflare.inc`. Сам факт наличия этого файла не доказывает, что DNS домена проксируется через Cloudflare; это нужно уточнить у пользователя.

Для ответов получения задания и ACK предусмотреть `Cache-Control: no-store`. Потоковая передача для long polling не требуется: сервер возвращает один готовый JSON после ожидания, поэтому оснований менять `proxy_buffering` сейчас нет.

Выводы и уточнения реализации:

- Начать с существующих `pm.max_children=8` и `memory_limit=128M`, без увеличения. При 3 ожидающих запросах остаётся до 5 воркеров на ACK, создание заданий и остальные запросы сайта. Кратковременные перекрытия запросов при переподключении также учитывать.
- Один снимок RSS не является верхней оценкой памяти воркера и включает разделяемые страницы. Не рассчитывать безопасный размер пула простым умножением этого значения.
- Заполненный swap сам по себе не доказывает текущую нехватку RAM. До изменения ресурсов получить `vmstat 1 10` и оценить текущий обмен со swap; окончательный вывод сделать при проверке под рабочей нагрузкой.
- Заявленный рабочий размер PDF до 300 КБ существенно ниже исходного клиентского ограничения 50 МБ. Для такого размера оснований увеличивать память PHP сейчас нет; проверить пиковую память на реальной наклейке. Не вводить новый жёсткий предел 300 КБ без отдельного решения по совместимости.
- Три места при интервале 500 мс дают примерно 6 попыток проверки очереди в секунду во время простоя. Проверить план запроса и работу индексов на MariaDB.
- `MaxRequestWorkers=150` не указывает на необходимость увеличения для трёх ожидающих запросов. Это общий лимит Apache на сервере, а не резерв для одного сайта; свободная ёмкость под нагрузкой ещё не измерена.
- Последующий SQL-запрос подтвердил MariaDB 10.11.9 и InnoDB: использовать поддерживаемый `FOR UPDATE SKIP LOCKED`, а не исходить из предположения о MySQL 8.
- Не менять параметры FPM, Apache и память заранее. Решение о расширении ресурсов принимать по задержкам ACK/создания заданий, активности swap и занятости пула во время приёмки.
