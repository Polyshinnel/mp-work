Печать наклеек: long polling и рабочие места
27 окт. 2026 г. · @Someone
Клиент печати переходит с опроса раз в 5 секунд на long polling: сервер держит запрос до 25 секунд и отвечает, как только появилась наклейка. От CRM нужно три вещи: отвечать в долгом режиме, принимать подтверждение получения и класть каждое задание в очередь того рабочего места, где нажали «Завершить упаковку».
Как клиент работает сейчас (протокол v1)
Клиент сам опрашивает сервер: раз в 5 секунд на каждое рабочее место он делает GET {адрес}/{место}. Адрес по умолчанию — https://mp.kidsberry.org/print/get-labels, то есть место 1 опрашивает https://mp.kidsberry.org/print/get-labels/1. Номер места передаётся только в пути, URL-кодированным.
Ответ с заданием — HTTP 200, JSON:
{
  "task_id": "42544",
  "filename": "label.pdf",
  "mime_type": "application/pdf",
  "encoding": "base64",
  "content": "JVBERi0xLjQK...",
  "size": 23086
}
Ответ без задания — HTTP 200, {"message": "No job found"} без поля task_id.
Что клиент проверяет в ответе (нарушение — задание отбрасывается с ошибкой в журнале клиента):
Поле
Требование
task_id
Обязательно. Строка или число; после приведения к строке — ^[A-Za-z0-9._-]{1,100}$. Должен быть уникальным навсегда: по нему клиент отсекает повторы (завершённые задания хранит 7 дней)
mime_type
Обязательно, ровно application/pdf
encoding
Обязательно, ровно base64
content
Обязательно. Строгий base64, после декодирования начинается с %PDF-, не больше 50 МБ
size
Необязательно. Если есть — точный размер PDF в байтах после декодирования
filename
Необязательно, только для журнала
Любой ответ не 2xx или не JSON клиент считает ошибкой связи: показывает жёлтый статус и повторяет запрос через 5, 10, 20, 30 секунд. Поэтому при ошибке не стоит отдавать 200 со страницей HTML.
Рабочие места
Каждое задание должно храниться с номером места, и сервер отдаёт клиенту только задания того места, которое указано в пути запроса. Один клиент на компьютере с принтерами опрашивает все места параллельно (/get-labels/1, /get-labels/2) и печатает задания места N на принтере, который в настройках клиента привязан к месту N.
Сейчас CRM кладёт все задания на место 1, и второй принтер без этой доработки не заработает. Нужно:
1. Место на экране упаковки. Выбор «Рабочее место: 1 / 2», запомненный в localStorage браузера на этом компьютере и показанный на экране. Привязка к браузеру надёжнее привязки к сотруднику: сотрудники меняются местами, а стол с принтером остаётся.
2. Место в запросе «Завершить упаковку». Сервер сохраняет его в задании печати. Если место не выбрано, кнопку блокировать с подсказкой, иначе наклейка никуда не уйдёт.
3. Выдача строго по месту. GET /print/get-labels/2 возвращает только задания места 2. Задание места, которое никто не опрашивает, просто ждёт и не уходит другим местам.
Формат номера места: ^[A-Za-z0-9_-]{1,32}$, сравнение точное как строки («1» и «01» — разные места). Номера в CRM должны совпадать с номерами в настройках клиента печати.
Протокол v2: long polling и подтверждение получения
В v2 добавляются две вещи: сервер держит запрос, пока не появится задание, и клиент подтверждает каждое полученное задание. Формат тела ответа не меняется.
Зачем подтверждение. Сейчас сервер считает задание выполненным в момент ответа. Если связь оборвалась посреди ответа или клиент закрыли, наклейка пропадает молча. С долгими запросами такое окно становится шире, поэтому делаем оба изменения вместе.
Запрос задания: GET /print/get-labels/{место}?wait=25
Что
Значение
Смысл
Заголовок запроса X-Print-Protocol
2
Клиент умеет v2 и будет подтверждать задания
Параметр wait
целое, 0–25 с
Сколько секунд сервер может держать запрос. Нет или 0 — ответить сразу. Больше 25 — сервер урезает до 25
Заголовок ответа X-Print-Protocol
2
Сервер обработал запрос по v2. Ставить в каждый ответ на v2-запрос, с заданием и без. Без него клиент работает как со старым сервером: ждёт 5 с между запросами и не подтверждает
Поведение сервера на v2-запрос:
• Задание для места уже есть или появилось за время ожидания — сразу ответить им (одно задание на ответ) и пометить его «отправлено», а не «выполнено».
• Задания так и не появилось за wait секунд — ответить {"message": "No job found"}.
• После любого ответа клиент сразу присылает следующий запрос, но не чаще раза в секунду, если пустые ответы приходят мгновенно.
Подтверждение: POST /print/get-labels/{место}/ack, заголовок X-Print-Protocol: 2, тело {"task_id": "42544"} (JSON).
• Клиент шлёт его, когда PDF уже надёжно сохранён в локальной очереди на диске. Это не означает «напечатано»: дальше за печать и повторы отвечает клиент.
• Ответ: 200 (тело клиент не читает). Повторное подтверждение того же задания тоже 200. Задания нет или оно чужого места — 404.
• Задание в статусе «отправлено» без подтверждения дольше 60 секунд сервер возвращает в очередь и отдаёт снова следующему запросу того же места. Клиент узнаёт повтор по task_id, повторно не печатает и просто подтверждает ещё раз.
Статусы задания на сервере: queued → sent (отдано в ответе, ждём подтверждения) → delivered (подтверждено). Из sent по таймауту 60 с — обратно в queued.
Один цикл обмена
Клиент всегда держит один открытый запрос на место, поэтому задание уходит к нему в ту же секунду, когда сервер его создал. Подтверждение приходит до печати, сразу после сохранения PDF на диск.
Реализация на сервере
Нужны три вещи: статус и место у каждого задания, атомарная выдача одного задания и цикл ожидания с таймаутами, которые не оборвут запрос раньше 25 секунд.
Хранение. В таблице заданий печати (дальше print_tasks, название условное) нужны поля seat_id, status (queued / sent / delivered), sent_at, delivered_at, send_count и индекс (seat_id, status, id).
Атомарная выдача. Два запроса одного места могут ждать одновременно (перезапуск клиента, смена настроек), поэтому задание нужно забирать так, чтобы его получил ровно один. PostgreSQL или MySQL 8:
BEGIN;
SELECT id FROM print_tasks
 WHERE seat_id = :seat
   AND (status = 'queued'
        OR (status = 'sent' AND sent_at < NOW() - INTERVAL '60 seconds'))
 ORDER BY id
 LIMIT 1
 FOR UPDATE SKIP LOCKED;
-- нашли :id — помечаем и отдаём
UPDATE print_tasks
   SET status = 'sent', sent_at = NOW(), send_count = send_count + 1
 WHERE id = :id;
COMMIT;
В MySQL интервал пишется INTERVAL 60 SECOND. Повторная выдача неподтверждённых заданий уже встроена в условие выбора, отдельный крон не нужен.
Цикл ожидания (псевдокод):
v2   = заголовок X-Print-Protocol == "2"
wait = min(int(query.wait or 0), 25)
deadline = now() + wait
loop:
    task = claim(seat, v2)        # v2: queued -> sent;  v1: queued -> delivered
    if task: return 200 json(task), заголовок X-Print-Protocol: 2 (если v2)
    if now() >= deadline: return 200 {"message": "No job found"}, тот же заголовок
    sleep(0.5)                    # транзакции и блокировки на время сна не держать
Проверка раз в 0,5 с — это до 4 лёгких запросов в секунду на два места по индексу. Если есть Redis, можно ждать события (BLPOP print:seat:2 0.5) и публиковать его при создании задания, но это необязательно. Если обработчик открывает PHP-сессию, закройте её до цикла (session_write_close()), иначе другие запросы с той же сессией застрянут.
Подтверждение: UPDATE print_tasks SET status = 'delivered', delivered_at = NOW() WHERE id = :task AND seat_id = :seat. Обновилась строка или задание уже delivered — 200, иначе 404.

Long polling и подтверждения
Важно: для запросов без заголовка сервер не должен ждать подтверждения. Иначе старому клиенту одно и то же задание будет приходить каждые 60 секунд бесконечно.
Рекомендуемый порядок:
1. Выкатить сервер и пройти проверку из следующего раздела на неиспользуемом месте (например, 99). Работающий старый клиент при этом не заметит разницы.
2. Выкатить выбор рабочего места на экране упаковки.
3. Поставить новый клиент на компьютер с принтерами, старый закрыть.
В настройках нового клиента длина ожидания задаётся полем long_poll_seconds в config.json (по умолчанию 25, 0 — выключить long polling).
Проверка
Всё проверяется из консоли на месте 99, которое никто не опрашивает, поэтому работающая печать не заденется.
BASE=https://mp.kidsberry.org/print/get-labels

# 1. Долгий запрос без заданий: висит ~25 с, потом No job found + X-Print-Protocol: 2
time curl -i -H 'X-Print-Protocol: 2' "$BASE/99?wait=25"

# 2. Старый режим: ответ сразу, без заголовка X-Print-Protocol
time curl -i "$BASE/99"

# 3. Подтверждение (task_id из ответа с заданием)
curl -i -X POST -H 'X-Print-Protocol: 2' -H 'Content-Type: application/json' \
     -d '{"task_id": "12345"}' "$BASE/99/ack"
Чек-лист приёмки:
[ ] Команда 1 висит 25 с и возвращает No job found с заголовком X-Print-Protocol: 2.
[ ] Пока команда 1 ждёт, создать задание для места 99 — она возвращает его меньше чем за секунду.
[ ] Без подтверждения то же задание (тот же task_id) приходит снова через 60 с.
[ ] После команды 3 задание больше не приходит; повторная команда 3 снова даёт 200.
[ ] Подтверждение с чужим местом или несуществующим task_id даёт 404.
[ ] Задание места 98 не приходит на запрос места 99.
[ ] Два параллельных долгих запроса места 99 и одно задание: получает ровно один, второй дожидается своих 25 с.
[ ] Команда 2 отвечает сразу, а выданное ей задание сразу становится delivered и не возвращается.
[ ] С экрана упаковки с выбранным местом 2 задание создаётся с seat_id = 2; без выбранного места кнопка недоступна.
После этого — сквозная проверка с клиентом: в его окне состояния наклейка с экрана упаковки должна появиться как «Последняя печать» через 1–3 секунды после нажатия кнопки.
Для сверки есть эталонная реализация серверной стороны на Python (~170 строк, без зависимостей): tools/fake_print_server.py в проекте клиента, просите у владельца. Клиент 0.3 против неё проходит сквозные тесты: задание уходит на печать через 16–62 мс после появления на сервере, при потерянном подтверждении печатается один раз.

[ ] На чём написан бэкенд и как он запущен (PHP-FPM, gunicorn, Node)? Это определяет, какие таймауты и лимиты воркеров из таблицы выше нужно поменять.
[ ] Сколько времени уходит на получение наклейки у Озона и Маркета после нажатия кнопки? После перехода на long polling это станет главной частью задержки.
